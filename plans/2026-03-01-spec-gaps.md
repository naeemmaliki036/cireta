## 1. Architecture Decision: FastAPI vs NestJS

### Context
The spec calls for NestJS (TypeScript). We built FastAPI (Python). Both are production-grade. The question is whether the divergence matters enough to migrate.

### FastAPI (keep)
**Pros:**
- Already built, tested (108 tests passing), working
- Python async is excellent for I/O-heavy workloads
- Pydantic v2 is faster than class-validator for validation
- SQLAlchemy async is mature and well-suited to this schema
- Smaller team: one language to maintain across backend
- `arq` or `celery[redis]` handles background jobs
- `fastapi-mail` or `boto3` (SES) handles email

**Cons:**
- Spec says NestJS — diverges from written architecture doc
- BullMQ is Node-native (need arq/celery instead)
- TypeScript-only shops prefer full-stack TS

**Migration cost if switching to NestJS:**
- ~4,000 LOC of Python to rewrite in TypeScript
- All 108 tests to rewrite in Jest
- SQLAlchemy → Prisma/TypeORM migration
- FastAPI → NestJS endpoint-by-endpoint translation
- Estimate: **40-60 hours of focused work**, high regression risk

### ✅ Recommendation: KEEP FastAPI

The platform works. Migrating NestJS is a 2-week rewrite with no user-visible benefit. The spec is a reference document — the actual business value is a working, compliant platform. Update the spec to reflect FastAPI rather than migrate.

**Additional Python packages needed:**
```
arq                    # Redis-backed background job queue (BullMQ equivalent)
redis[asyncio]         # async Redis client (aioredis merged into redis-py 4.2+)
fastapi-mail           # Email sending (SMTP/SES wrapper)
slowapi                # Rate limiting for FastAPI (brute force protection)
itsdangerous           # Signed tokens for email verify / password reset links
python-multipart       # File uploads (token documents)
boto3                  # AWS SES (alternative to SMTP)
```

**Signature verification (SIWE-style):**
```python
# POST /wallets body:
# { address: str, signature: str, nonce: str }
# Message format: "Link wallet to Cireta account: {nonce}"
# Verify: eth_account.recover_message(message, signature) == address

from eth_account.messages import encode_defunct
from eth_account import Account

def verify_wallet_signature(address: str, signature: str, nonce: str) -> bool:
    message = encode_defunct(text=f"Link wallet to Cireta account: {nonce}")
    recovered = Account.recover_message(message, signature=signature)
    return recovered.lower() == address.lower()
```

## 3. Technology Recommendations

| Need | Recommendation | Reason |
|------|---------------|--------|
| Email | `fastapi-mail` + SendGrid SMTP | Zero infra, $0 for <100/day, easy templates |
| Redis client | `redis[asyncio]` (redis-py 4.2+) | aioredis merged in, one package |
| Background jobs | `arq` | Async-native, Redis-backed, simple API, no Celery overhead |
| Notifications delivery | **Polling** (30s interval) | Simple, no WebSocket infra; upgrade to SSE in Phase 2 |
| ONCHAINID | Tokeny's `@onchain-id/identity-sdk` (npm) | Official SDK; deploy from backend via web3.py call to factory |
| Safe detection | `viem`: `publicClient.getCode({ address })` then check `!= '0x'` | Standard pattern, no extra deps |
| TanStack Query | Wrap existing `useEffect` fetches → `useQuery()` hooks | Zero API changes, massive DX improvement, auto-refetch, caching |
| State management | Zustand store for auth state, wallet state | Replaces scattered useState across components |
| CSV export | Python `csv` stdlib in backend — no extra dep needed | |
| IPFS upload | `pinata-web3` SDK | For token document uploads in the creation wizard |

## 4. Risk Assessment

### FastAPI vs NestJS — risk of staying
**Risk level: LOW**
- No user-visible impact
- All integrations work identically
- The spec document should be updated to say FastAPI
- Only risk: hiring a NestJS developer who doesn't know Python

### localStorage refresh token — security risk
**Risk level: HIGH**
- XSS attack can steal refresh token → permanent account access
- Fix in Phase A is mandatory before production
- Mitigation now: short access token TTL (15min) limits blast radius
- Priority: fix before any real user data enters the system

### Smart contract audit risk (missing claimRefund / OTC exclusion)
**Risk level: CRITICAL for production**
- Missing `claimRefund()`: investors in failed sales cannot get USDC back — **funds stuck**
- Missing OTC fee exclusion: issuer overpays fees on bank-transferred deals
- Missing `fee_cap_usdc`: uncapped fees on large raises could exceed agreed maximums
- **None of these are mainnet yet** — fix before any real deployment
- All three are Phase G work, ~2h of Solidity

### The Graph subgraph — risk of skipping
**Risk level: MEDIUM**
- Without it, the frontend relies entirely on backend DB (which relies on tx submissions)
- If a tx is submitted but backend misses the event → data inconsistency
- Acceptable for Phase 1-2, essential before mainnet at scale

### ONCHAINID not wired — risk
**Risk level: HIGH for compliance**
- The on-chain identity check is the core security guarantee of ERC-3643
- Without ONCHAINID deployment on KYC approval, tokens can't actually enforce compliance on-chain
- Smart contracts exist but aren't being called from backend
- Fix: add `deploy_onchainid_task` to arq queue in KYC webhook handler
