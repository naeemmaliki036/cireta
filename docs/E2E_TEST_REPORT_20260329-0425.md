## 4. Bug Fixes

### 4.1 T9 — List Token Documents (500 → 200)

**Endpoint:** `GET /api/v1/tokens/{token_id}/documents`

**Root cause:** The `token_documents` database table had a column named `uploaded_at`, but the `TokenDocument` model inherits `created_at` from `BaseModel`. SQLAlchemy generated a query referencing `token_documents.created_at` which didn't exist in the DB.

**Fix:** Renamed the database column:
```sql
ALTER TABLE token_documents RENAME COLUMN uploaded_at TO created_at;
```

**File:** Database schema (Railway PostgreSQL)

### 4.2 N3 — Notification Preferences (500 → 200)

**Endpoint:** `GET /api/v1/notifications/preferences`

**Root cause:** When creating a new `NotificationPreferences` record for a user who didn't have one, `BaseModel.updated_at` defaulted to `None` on insert. However, the database column had a `NOT NULL` constraint (`DEFAULT now()`). SQLAlchemy sent an explicit `NULL`, overriding the DB default.

**Fix:** Changed `BaseModel.updated_at` from nullable default to insert default:

```python
# Before (packages/common/models/base.py)
updated_at: Mapped[datetime | None] = mapped_column(
    DateTime(timezone=True),
    default=None,
    onupdate=lambda: datetime.now(UTC),
)

# After
updated_at: Mapped[datetime] = mapped_column(
    DateTime(timezone=True),
    insert_default=datetime.now,
    onupdate=lambda: datetime.now(UTC),
)
```

**File:** `packages/common/models/base.py`

### 4.3 S12 — OTC Allocate (500 → 200)

**Endpoint:** `POST /api/v1/sales/{sale_id}/otc`

**Root cause:** OTC contributions look up the investor by wallet address in the `wallets` table. If the wallet isn't registered (common for OTC investors), `investor_user_id` was set to `None`, violating the `contributions.user_id` NOT NULL constraint.

**Fix:** Fall back to the issuer's `user_id` when no investor wallet is found:

```python
# Before (apps/api/api/v1/endpoints/sales.py)
investor_user_id = investor_wallet.user_id if investor_wallet else None

# After
investor_user_id = investor_wallet.user_id if investor_wallet else user_id
```

**File:** `apps/api/api/v1/endpoints/sales.py`

## 9. Deep Dive: S8 (Deploy Sale) & S7 (On-chain Status)

### 9.1 S8 — Deploy Sale: Full Call Flow

When `POST /api/v1/sales/{sale_id}/deploy` is called, the following chain executes:

```
1. Endpoint (apps/api/api/v1/endpoints/sales.py:175)
   → Validates the caller is the issuer who owns this sale
   → Checks that the token has been deployed on-chain (has contract_address)
   → Determines sale mode: "vested" vs "direct"
   → Seeds the sale is VESTED mode (set in seed data as SaleMode.VESTED)

2. Calls Web3SaleService.deploy_sale_vested() (apps/api/services/web3_sale_service.py:91)
   → Gets CiretaSaleFactory contract via ContractRegistry
   → Encodes Sale.initialize() calldata with 10 parameters:
     - token_address, payment_token, identity_registry
     - issuer_wallet, fee_manager
     - soft_cap, hard_cap, fee_basis_points, fee_cap_usdc
     - _initialOwner (set to SaleFactory address, NOT issuer)
   → Submits factory.deploySaleVested() transaction with gas_limit=5,000,000

3. On-chain: CiretaSaleFactory.deploySaleVested()
   → Deploys a new Sale ERC1967Proxy (clone of Sale implementation)
   → Calls fractionFactory.deployVaultAndFraction()  ← CRITICAL STEP
   → Calls sale.setVestedMode(vault, fractionToken)
   → Transfers Sale ownership from SaleFactory to issuer
   → Emits SaleDeployed event

4. On-chain: CiretaFractionFactory.deployVaultAndFraction() [onlyOwner]
   → Deploys CiretaVault proxy (ERC1967Proxy of vault implementation)
   → Deploys CiretaFractionToken proxy (ERC1967Proxy of fraction implementation)
   → Calls vault.setFractionToken(fractionProxy)
   → Transfers vault ownership to admin (issuer)
   → Emits VaultDeployed event

5. Back in Python: parse receipt for events
   → Parse SaleDeployed from SaleFactory → extract sale_address
   → Parse VaultDeployed from FractionFactory → extract vault_address, fraction_address
   → Save all three addresses to the database
```

### 9.2 The Two Errors Encountered (in chronological order)

#### Error A: `OwnableUnauthorizedAccount` (Run 3)

```
error=('0x118cdaa7...0x6d821c1f5c72fd6a4e194c0ff76826ba6a5ab55d')
```

- `0x118cdaa7` is the Solidity selector for `OwnableUnauthorizedAccount(address)`
- The address in the error is the SaleFactory (`0x6d8...55d`)
- **Cause:** `CiretaFractionFactory.deployVaultAndFraction()` has an `onlyOwner` modifier. The FractionFactory was still owned by the deployer wallet (`0xaC7...dA7`), but the SaleFactory (`0x6d8...55d`) was calling it.
- **Fix applied:** Ran `contracts/scripts/transfer-fraction-ownership.ts` which called `fractionFactory.transferOwnership(saleFactoryAddress)`. Confirmed ownership transferred on-chain.

#### Error B: `settings.fraction_factory_address is empty` (Run 4)

```
error=Address for 'CiretaFractionFactory' not configured (settings.fraction_factory_address is empty).
```

- After the on-chain transaction completes, the Python code needs to parse the `VaultDeployed` event from the FractionFactory contract (web3_sale_service.py:166).
- To do this, `ContractRegistry.get_contract("CiretaFractionFactory")` is called, which looks up `settings.fraction_factory_address` via the `_ADDRESS_MAP`.
- The `FRACTION_FACTORY_ADDRESS` env var was not set when the API was started.
- **Fix applied:** Added `FRACTION_FACTORY_ADDRESS=0xec591AC67443De54D338beBBeF4275e4188E980F` to `.env`.

### 9.3 Contract Registry Resolution

The `ContractRegistry` (apps/api/core/contract_registry.py) maps contract names to settings attributes:

```python
_ADDRESS_MAP = {
    "CiretaTokenFactory":    "token_factory_address",
    "CiretaSaleFactory":     "sale_factory_address",
    "CiretaFractionFactory": "fraction_factory_address",    # ← was empty
    "IdentityRegistry":      "identity_registry_address",
    "IdentityFactory":       "identity_factory_address",
    "ModularCompliance":     "modular_compliance_address",
}
```

ABIs are loaded from Hardhat artifacts at `contracts/artifacts/src/`. The registry searches recursively for `<Name>.json`, filtering out `.dbg.json` files.

### 9.4 Potential Remaining Risk

The `issuer.wallet_address` in the seed data is a dummy address (`0xbbbbbb...bb`). The deploy endpoint (sales.py:212) uses this as the `issuer_wallet` parameter:

```python
issuer_addr = sale.issuer.wallet_address or web3_sale.tx_svc._account.address
```

Since the seed sets a non-empty dummy address, it will NOT fall back to the deployer. If the Sale or IdentityRegistry contract validates that the issuer wallet is a registered on-chain identity, the transaction could revert with an identity-related error.

**Mitigation options if this occurs:**
1. Clear the issuer's `wallet_address` in the seed so it falls back to the deployer address
2. Use the deployer address explicitly as `issuer.wallet_address` in the seed
3. Register the dummy address in the IdentityRegistry before deploying the sale
